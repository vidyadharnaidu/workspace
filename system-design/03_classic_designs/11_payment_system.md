# Design a Payment System (Stripe checkout / e-commerce payments)

> **Remember:** *"Idempotency keys on every API, a payment state machine, a card processor (PSP) behind an adapter, a double-entry immutable ledger, webhooks + polling for final status, outbox for events, and daily reconciliation. Money flows need correctness over availability."*

## 1. Requirements

**Functional**
- Pay for an order with a card/wallet through a payment service provider (PSP: Stripe, Adyen, Braintree)
- Refunds (full/partial)
- Record every money movement in a ledger; merchant balances and payouts
- Payment status visible to users and merchants

**Non-functional**
- **Never double charge, never lose a payment** (exactly-once *effect*)
- Strong consistency and auditability; security/compliance (PCI DSS: we never store raw card data)
- High availability, but correctness > availability (it's OK to reject and let the user retry)

## 2. Estimates
- 10M transactions/day → ~120 TPS average, peaks ×10 (sales events). Volume is modest, so **correctness is the challenge**, not scale. A sharded SQL DB is fine.

## 3. API
```
POST /v1/payments
  Headers: Idempotency-Key: 7b1e...        (generated by the client per checkout attempt)
  { orderId, amount: 4999, currency: "USD", paymentMethodToken: "pm_tok_..." }
  -> 201 { paymentId, status: "PROCESSING" | "SUCCEEDED" | "REQUIRES_ACTION" | "FAILED" }
GET  /v1/payments/{id}
POST /v1/payments/{id}/refunds   (Idempotency-Key)  { amount }
POST /webhooks/psp               (signed by PSP)   payment events
```
Card numbers go from the browser/app **directly to the PSP** (hosted fields / SDK), which returns a **token**. Our servers only see the token, keeping us out of most PCI scope.

## 4. Data model (SQL, ACID)
```
payments        (payment_id PK, order_id, idempotency_key UNIQUE, amount, currency, status,
                 psp_reference, created_at, updated_at, version)
payment_events  (event_id, payment_id, from_status, to_status, payload, created_at)   -- audit trail
ledger_entries  (entry_id, transaction_id, account_id, direction DEBIT|CREDIT, amount, currency, created_at)  -- append-only
accounts        (account_id, type: CUSTOMER_FUNDS|MERCHANT_PAYABLE|FEES|..., currency)
idempotency     (key PK, request_hash, response_body, status, expires_at)
outbox          (id, aggregate_id, event_type, payload, published_at NULL)
```

## 5. High-level design

```
 Client --token from PSP SDK--> [Checkout / Order Service]
                                        |
                                        v  (Idempotency-Key)
                                [Payment Service] ---- state machine ----> [Payments DB + Ledger + Outbox]  (one transaction)
                                        |
                                        v
                                [PSP Adapter] --HTTPS (idempotency key)--> [ PSP: Stripe/Adyen ] --> card networks / banks
                                        ^                                          |
                                        |<---------- signed webhooks --------------+
                                        |<---------- status polling for stuck payments (reconciler job)
 [Outbox relay] -> [Kafka: payment_succeeded ...] -> Order Service (mark paid), Notifications, Analytics
 [Reconciliation job, daily] : compare our ledger vs PSP settlement files -> flag mismatches
 [Payout service]            : merchant balances from ledger -> bank transfers
```

## 6. Deep dives

### Idempotency (no double charge)
1. The client sends an `Idempotency-Key` (per checkout attempt, reused on retries).
2. The server inserts the key into the `idempotency` table (UNIQUE).
   - Already exists and **completed** → return the stored response.
   - Exists and **in progress** → return 409 / "processing".
3. Forward to the PSP with **the same idempotency key**, so even if our request times out and we retry, the PSP charges only once.

### Payment state machine
```
CREATED -> PROCESSING -> SUCCEEDED -> (PARTIALLY_)REFUNDED
               |    \-> REQUIRES_ACTION (3-D Secure) -> PROCESSING
               \-> FAILED
```
- Transitions happen with **optimistic locking** (`UPDATE ... SET status=?, version=version+1 WHERE payment_id=? AND version=?`). Illegal transitions are rejected.
- **Unknown outcome** (timeout talking to the PSP): mark it `PROCESSING`, never guess. Webhooks and polling resolve it.

### Double-entry ledger
Every money movement is a transaction of **balanced** entries (sum of debits = sum of credits), append-only (corrections are new reversing entries, never updates).

```
Customer pays $100, platform fee $3:
  DEBIT   customer_funds_receivable   100
  CREDIT  merchant_payable             97
  CREDIT  platform_fee_revenue          3
```
Balances = SUM(entries) per account, cached as snapshots. This makes auditing and reconciliation possible.

### Events without losing them
The payment status change + ledger entries + an **outbox row** are written in one DB transaction. A relay publishes the outbox to Kafka. Consumers (order service) are idempotent by payment id.

### Reconciliation
Daily, compare the PSP settlement report ↔ our ledger ↔ bank statements. Mismatches (missing webhook, duplicated capture, fee differences) go to an exceptions queue for automated fixes or ops.

## 7. Trade-offs
- Synchronous authorization (user waits ~1–3 s) vs async capture/settlement.
- Strong consistency (SQL, single-writer per payment) over availability: return a clear "try again".
- Multiple PSPs (routing by cost/success rate, failover) add complexity, so hide them behind one adapter interface.

## 8. Follow-up questions
- **The PSP charged the card but our server crashed before saving.** The payment stays `PROCESSING`. The webhook or reconciler polls the PSP by idempotency key/reference and completes the state. The user isn't charged twice because the retry reuses the key.
- **Refund more than paid?** The ledger/state check within a transaction: `refunded_total + amount <= captured`.
- **Currency?** Store amounts as **integer minor units** (cents) plus a currency code. Never use floating point. FX conversion is its own ledger transaction.
- **Fraud?** A risk scoring service before authorization (velocity checks, device fingerprint, ML), plus 3-D Secure for risky payments.
